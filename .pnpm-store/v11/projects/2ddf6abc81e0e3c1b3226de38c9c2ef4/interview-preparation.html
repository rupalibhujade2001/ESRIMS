FarmLink Interview Preparation

Java Full Stack Developer — 2 years of experience

Project summary: FarmLink is a B2B agricultural wholesale marketplace. Farmers create and manage bulk-produce listings, while buyers browse available products and save enquiry drafts. The React frontend connects to Auth, Product, and Inventory services designed with Java Spring Boot microservices.

Project Overview

1. Explain your project.

FarmLink connects farmers directly with wholesale buyers such as retailers, hotels, and processors. Farmers can log in and create, update, or delete bulk produce listings. Buyers can browse products, view available stock, and save enquiry drafts. The frontend is built with React and Vite. The backend architecture uses Spring Boot services for authentication, products, and inventory.

2. What technologies did you use?

The frontend uses React 19, JavaScript, Vite, CSS, Fetch API, and browser localStorage. The backend architecture uses Java, Spring Boot REST APIs, JWT-based authentication, and Kafka-based asynchronous communication for inventory-related events.

3. Explain the frontend architecture.

App.jsx coordinates the application state, navigation, authentication token, products, dashboard data, notifications, and modal visibility. UI is split into feature-focused components such as Marketplace, LoginModal, ProductForm, SellerDashboard, and Inventory. API calls are centralized in src/services/api.js.

4. What are the main user roles?

The current UI supports FARMER and ADMIN login roles. The application also provides a buyer workspace view. Farmers can manage their own product listings, while buyers can browse listings and save enquiry drafts.

Authentication and Security

5. How does authentication work?

The frontend sends credentials to POST /auth/login. On success, it receives a token, email, and role. The token and email are stored in localStorage. Protected requests send the token through the header Authorization: Bearer <token>. On logout, the application removes those localStorage values and resets protected UI data.

6. What is JWT, and why is it useful?

JWT is a signed token used to identify an authenticated user. After login, the client attaches it to protected API requests. It works well with microservices because services can validate the token without maintaining traditional server-side sessions.

7. How do you implement role-based access?

The frontend checks the role before allowing a product listing to be created. Only a FARMER can open the product form. It also shows Edit and Delete only when the logged-in email matches the listing owner. However, this is only a UI check; Spring Security must enforce authorization and ownership on the backend.

8. How would you improve token security in production?

I would use short-lived access tokens, refresh tokens, HTTPS, secure HTTP-only cookies where appropriate, token expiration handling, and centralized validation through Spring Security or an API gateway. Passwords must be hashed using BCrypt.

9. Why did you create a separate API service file?

Centralizing API calls in api.js avoids repeated Fetch configuration in UI components. It makes the code easier to maintain, gives common error handling, and keeps components focused on rendering and user interaction.

10. How do you handle API errors?

The reusable request function checks response.ok. If the response is unsuccessful, it reads a backend message when available and throws an error. Components use try-catch-finally to display a toast message and to reset loading state. Initial product and dashboard requests fall back to mock data if services are unavailable.

11. Why is Vite proxy configured?

During local development, Vite proxies /auth-api, /product-api, and /inventory-api to Spring Boot services on ports 8081, 8083, and 8084. This keeps frontend URLs clean and avoids CORS problems during development.

React and Frontend Questions

12. Why did you use useEffect?

I use useEffect to load products and dashboard data when the authentication token changes. It keeps asynchronous API side effects outside the render process and refreshes data after login.

13. Why did you use useMemo for product search?

The marketplace derives visible products by filtering on product name and category. useMemo recalculates this list only when the product array or search input changes, rather than on unrelated renders.

14. How does product create and update work?

The same ProductForm is reused. If an editing product exists, the app calls the update endpoint using its ID; otherwise it calls the create endpoint. Form values such as price and quantity are converted to numbers before sending to the API. After a successful save, the product list is reloaded.

15. What is the purpose of mock data?

Mock products and dashboard values let us develop and demonstrate the UI even when backend services are unavailable. When a live API succeeds, live data replaces the mock data.

16. What is a limitation in the current inventory loading approach?

The app requests inventory separately for every product after login. With a large catalog, this causes the N+1 API-call problem. I would improve it with a bulk inventory endpoint, pagination, caching, or an API response that combines product and stock summaries.

Java, Spring Boot, and Microservices

17. Explain the microservice design.

Auth Service handles login and JWT generation. Product Service manages product CRUD operations. Inventory Service manages available quantity, reserved quantity, low-stock items, and dashboard analytics. Separating these services allows independent deployment and scaling based on workload.

18. How does Kafka fit into FarmLink?

When a farmer creates a product, Product Service can publish a product-created event to Kafka. Inventory Service consumes it and creates the initial inventory record asynchronously. This reduces direct coupling between the two services and improves resilience.

19. What Kafka issues should you handle?

Important concerns are duplicate messages, retries, consumer failure, ordering, and eventual consistency. Consumers should be idempotent, events should have unique IDs, retries and dead-letter queues should be configured, and event processing should be monitored.

20. What validations would you apply in Spring Boot?

I would validate request DTOs using Bean Validation: @NotBlank for product name, @NotNull and @Positive for price and quantity, @Email for email, and appropriate size constraints for text fields. A @RestControllerAdvice can return a consistent validation error response.

21. How would you prevent overselling?

Inventory Service should reserve stock inside a database transaction. It should reduce available stock only when sufficient quantity exists. Optimistic locking with a version field, or suitable database-level locking, prevents two buyers from reserving the same stock at the same time.

22. Which entities would the backend have?

Core entities are User, Product, Inventory, Enquiry, and Order. User stores email, password hash, and role. Product stores farmer ownership and listing details. Inventory stores available and reserved quantities. Enquiry and Order would support the buyer-to-seller purchasing workflow.

Honest Current Scope and Future Improvements

23. Why are buyer enquiries stored in localStorage?

The current enquiry flow is a browser-only draft feature because an Enquiry or Order Service endpoint is not yet connected. localStorage preserves these drafts after page refresh. The next enhancement is to persist enquiries in a backend database and let sellers respond to them.

24. What would you improve next?

I would add real Enquiry and Order services, a bulk inventory API, pagination and server-side search, inventory update functionality, automated tests, TypeScript, React Query for server-state caching, refresh-token support, and accessibility improvements.

Strong answer: What was your contribution?

I worked on the application integration layer and frontend workflow: reusable React components, login integration, JWT handling, protected product operations, product search, seller ownership UI checks, inventory dashboard rendering, buyer enquiry drafts, centralized API handling, and fallback UI states for unavailable backend services.
